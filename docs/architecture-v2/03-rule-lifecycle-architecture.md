# 03 私有法则生命周期架构 (Rule Lifecycle)

## 1. 云原生法则账本的进化

PM-Agent 的商业壁垒在于其动态积累的“私有法则账本”。在云原生特化下，法则不再仅仅局限于“文案必须用敬语”这样的自然语言规范，它深入到了声明式基础设施（IaC）的骨架中。

## 2. 混合法则域与 Namespace 隔离

为了应对复杂的微服务集群，法则被隔离在不同的 Namespace（命名空间）中：

- **Global Space (全局空间)**：全公司的强制准则。例如公司的基础安全红线、跨集群访问的 mTLS 强制规范。
- **Local / Cluster Space (局部空间)**：精细到某个 Kubernetes Namespace 或某个特定业务 Repo 的独有业务法则。
- **IaC/GitOps 策略区**：存储结构化的配置基线检测规则（如 OPA/Gatekeeper Policies），诸如“所有对外暴露的 API 必须配置防抖与限流注解”。

## 3. 法则的自动化生命周期

系统内置 `RuleService` 守护进程，像管理微服务一样管理知识体系：

### 3.1 法则的诞生与解析
- 来源于历史仲裁与人工重构。对于云原生配置文件 (如 K8s YAML, Helm Values)，Agent 会通过 Diff 提取结构化变更，沉淀为自动检测规则。

### 3.2 冲突检测与仲裁
- 新增法则时（尤其是基础设施规则），与现有网格约束进行检测。
- 发现严重互斥（如新法则放行了一个被全局策略拦截的端口）时，触发预警交由人类用户进行裁决。

### 3.3 老化降级与淘汰 (Eviction Policy)

#### 3.3.1 规则分级体系

为防止低频但关键的规则被静默淘汰，所有法则必须在创建时分配一个**保护等级 (Protection Level)**：

| 等级 | 行为 | 适用场景 |
|---|---|---|
| `CRITICAL` | 永不自动淘汰，只能人工操作归档。任何降权尝试触发审计事件并要求人工确认。 | 安全红线、合规强制策略（如 mTLS、数据加密） |
| `STANDARD` | 正常 LRU + 命中率衰减淘汰 | 业务逻辑规则、文案规范 |
| `DEPRECATED` | 人工标记为废弃，进入归档区 | 已确认不再适用的旧规则 |

#### 3.3.2 STANDARD 规则的淘汰机制

对于 `STANDARD` 等级的法则，采用基于 LRU + 命中率衰减的淘汰机制：
- 随着底层架构演进（如从 K8s 迁移到 Serverless），那些绑定旧架构的陈旧法则，会因为**长时间未被命中 (Time decay)** 降低权重。
- 最终降至阈值以下的法则将被剥离至”归档区 (Archive)”，避免干扰新一轮的意图路由检索，保持企业大脑的高效敏捷。

#### 3.3.3 CRITICAL 规则的保护机制

对于 `CRITICAL` 等级的法则，系统严格禁止自动淘汰：
- 即使长时间未命中，权重保持不变。
- 若系统检测到 CRITICAL 规则的命中率为零超过配置阈值（如 180 天），不执行淘汰，但产生 `RuleHealthCheckEvent` 推送给管理员，提示”此规则长期未触发，请确认是否仍然需要”。
- 管理员可以选择：保留（确认仍需要）、降级为 STANDARD（接受自动淘汰风险）、或手动 DEPRECATED。
- 所有 CRITICAL 规则的等级变更操作记录审计日志，不可被自动化流程静默执行。

#### 3.3.4 淘汰通知机制

任何规则被降权或归档时，系统必须：
1. 产生 `RuleEvictionEvent`，写入审计日志
2. 通过前端通知栏推送给 Workspace 管理员
3. 归档操作有 7 天冷静期，期间可一键恢复
